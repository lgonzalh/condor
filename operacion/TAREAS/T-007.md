# T-007 - Builder inicial

Version: 1.0.0
Estado: Cerrada y congelada (completada, verificada, integrada y publicada)
Prioridad: Alta

## Objetivo

Implementar la version inicial del Builder (ARQ-006 / FN-007): consumir el
`WorkPlan` entregado por T-006 y ejecutar un conjunto acotado y determinista
de cambios sobre el proyecto objetivo, siguiendo el flujo del Kernel
(Planner -> Builder -> Verifier). El Builder constituye el puente entre el
plan y la modificacion real del codigo.

El Builder no improvisa (ADN Condor): aplica cambios derivables del plan de
forma determinista, dentro de la frontera del proyecto objetivo detectado por
T-004, y sin depender del historial de conversaciones ni del LLM.

## Alcance

T-007 debe transformar el `WorkPlan` en cambios reales sobre el proyecto
objetivo dentro de los limites aprobados:

- Consumir el `WorkPlan` persistido (via `IStateStore.LoadPlanAsync`) y su
  `WorkingDirectory`, `Objective`, `Intention` y `Tasks`.
- Derivar un conjunto acotado de acciones de build (`BuildAction`) a partir de
  las tareas del plan, mediante heuristica textual determinista (patron D-E3),
  sin LLM.
- Soportar de forma minima dos tipos de operacion de archivo sobre el
  proyecto objetivo: **crear** archivo y **actualizar** archivo, mas la
  creacion de la estructura de directorios necesaria.
- Limitar toda escritura a la raiz del proyecto objetivo (`WorkingDirectory`
  del plan), sin salir de ella (frontera de seguridad).
- Producir un resultado de build (`BuildResult`) que registre, por cada accion,
  su estado (aplicada / omitida / fallida), ruta y evidencia.
- Exponer la capacidad mediante un comando publico nuevo: `condor construir`
  (texto y `--json`), en espanol sin tildes.
- Persistir `build.json` como artefacto derivado y transitorio en el estado
  local, sin escribir conocimiento permanente en el proyecto objetivo.

### Ambito de las operaciones

| Operacion | Comportamiento |
|---|---|
| Crear | Crea un archivo nuevo bajo `WorkingDirectory`, creando directorios intermedios si es necesario. No sobrescribe un archivo existente (se degrada a omision con motivo). |
| Actualizar | Sobrescribe el contenido de un archivo existente bajo `WorkingDirectory` con el contenido derivado. No crea el archivo si no existe (se degrada a omision con motivo). |
| Estructura | La creacion de directorios se realiza implicitamente al crear/actualizar rutas acotadas; no se expone como operacion aislada. |

## No alcance

T-007 NO debe:

- reimplementar el Planner (T-006) ni ampliar sus modelos congelados
  (`WorkPlan`, `PlanTask`, `PlanLimits`); el consumo es de solo lectura;
- re-ejecutar el descubrimiento de proyecto (T-004) ni la reconstruccion de
  contexto (T-005);
- usar red, servicios cloud ni descargas;
- usar el LLM local (Ollama) para generar el contenido de los cambios en esta
  version; el contenido se deriva directamente del plan;
- borrar archivos del proyecto objetivo (la eliminacion queda fuera del alcance
  inicial);
- escribir conocimiento permanente en el repositorio del proyecto objetivo;
- ejecutar comandos arbitrarios del sistema sobre el objetivo (sin shell);
- inventar rutas, contenidos ni evidencias sin base en el plan o en la
  solicitud.

## Frontera con T-006

T-006 produce el plan de trabajo (tareas ordenadas). T-007 consume ese plan
para derivar y aplicar cambios. T-007 no reimplementa la generacion del plan ni
modifica el `WorkPlan` congelado.

```
T-006: ProjectContext + solicitud del usuario -> interpretacion de intencion -> WorkPlan
T-007: WorkPlan -> derivacion de acciones -> cambio sobre el proyecto objetivo -> BuildResult
```

## Frontera con T-008 (Verificacion inicial)

T-008 (pendiente) es el Verifier (ARQ-007 / FN-008). T-007 no verifica la
correccion de los cambios aplicados; solo registra que la accion fue aplicada,
omitida o fallida con su evidencia. La verificacion de calidad pertenece a
T-008.

## Entradas

- `WorkPlan` persistido (via `IStateStore.LoadPlanAsync`): `Status`,
  `Reason`, `WorkingDirectory`, `Objective`, `Intention` y `Tasks`.
- Limites centralizados del build (`BuildLimits`).

## Salidas

- `BuildResult` con:
  - estado general del build y motivo de degradacion;
  - raiz del proyecto objetivo y directorio de trabajo;
  - intencion y objetivo del plan consumido;
  - lista de acciones (`BuildAction`) con estado, ruta, operacion y evidencia;
  - resumen: aplicadas / omitidas / fallidas;
  - limites aplicados;
  - metadata de generacion.
- Seccion `BUILD` en el resultado en texto de `condor construir`.
- Campo `build` en la salida de `condor construir --json`.

## Responsabilidades

| Capa | Responsabilidad |
|---|---|
| Condor.Core | Modelos de build (`BuildAction`, `BuildActionKind`, `BuildResult`, `BuildLimits`), logica pura de derivacion (`BuildDeriver`): sin IO, sin frameworks, determinista. |
| Condor.Infrastructure | `BuildService` (orquestacion de carga del plan, peticion de derivacion y aplicacion) y `ProjectFileWriter` (IO de archivos acotada a `WorkingDirectory`); persistencia de `build.json`. |
| Condor.Cli | Comando `condor construir` (texto y `--json`), ayuda y estado inicial. |

Ningun componente de T-007 modifica los modelos congelados de T-006 ni
persiste conocimiento permanente en el proyecto objetivo.

## Contrato del Builder

### Interfaz de servicio

En `Condor.Core.Contracts`, siguiendo el patron de `IPlanService`:

```
IBuildService
  Task<BuildResult> ApplyPlanAsync(CancellationToken cancellationToken = default)
```

`BuildService` (Infrastructure) implementa `IBuildService`: carga el
`WorkPlan` persistido, delega la derivacion pura de acciones en
`BuildDeriver` (Core) y aplica las acciones sobre el proyecto objetivo mediante
`ProjectFileWriter`.

### Modelo tecnico consolidado

El concepto de dominio "resultado de build" se materializa en
`Condor.Core.Models` con `SchemaVersion` propio, independiente de `WorkPlan`.

```
BuildAction
  Id                    string                       // "B0", "B1", ...
  Kind                  BuildActionKind              // Crear | Actualizar
  RelativePath          string                       // ruta relativa a WorkingDirectory
  Content               string
  Evidence              string                       // origen en el plan

BuildActionKind         enum                         // Crear, Actualizar

BuildResult
  SchemaVersion         string                       // "1.0.0"
  Status                DetectionStatus              // Detected | Limited | NotDetected | Error
  Reason                string?
  RootName              string
  WorkingDirectory      string
  Intention             string                       // del plan consumido
  Objective             string                       // del plan consumido
  Actions               List<BuildAction>
  Applied               int
  Omitted               int
  Failed                int
  LimitsApplied         List<string>
  GeneratedAtUtc        DateTime

BuildLimits
  MaxActions                    int                  // propuesto: 24
  MaxContentLength              int                  // propuesto: 64_000
  MaxRelativePathLength         int                  // propuesto: 260
  BuildTimeoutMilliseconds      int                  // propuesto: 15_000
  static Default              BuildLimits
```

`DetectionStatus` se reutiliza (patron D-D2); no se amplia.

### Contratos e interfaces

En `Condor.Core.Contracts`:

```
IBuildService
  Task<BuildResult> ApplyPlanAsync(CancellationToken cancellationToken = default)
```

`IStateStore` se extiende de forma aditiva (patron D-E4 / D-D4):

```
IStateStore
  Task SaveBuildAsync(BuildResult result, CancellationToken ct = default)
  Task<BuildResult?> LoadBuildAsync(CancellationToken ct = default)
```

Esta extension es aditiva y no altera contratos congelados.

### Flujo de datos

```
condor construir
  -> BuildCommand.ExecuteAsync(buildService, stateStore, args)
  -> BuildService.ApplyPlanAsync()
      -> stateStore.LoadPlanAsync()               // WorkPlan persistido (T-006)
      -> si no hay plan: BuildResult NotDetected (motivo instructivo)
      -> BuildDeriver.Derive(plan, BuildLimits.Default)     // logica pura
      -> ProjectFileWriter.Apply(actions, plan.WorkingDirectory)   // IO acotada
      -> BuildResult
  -> stateStore.SaveBuildAsync(result)            // persiste build.json (derivado)
  -> texto: BuildRenderer.RenderBuild(result)
    json: Console.WriteLine(BuildJson.Serialize(result))
  -> exit code: 1 si Status == NotDetected, si no 0
```

### Derivacion de acciones (logica pura)

`BuildDeriver.Derive(WorkPlan? plan, BuildLimits limits)` (Core, sin IO):

1. Si `plan` es null o `plan.Status == NotDetected`: devolver `BuildResult` con
   `Status = NotDetected` y motivo instructivo (ejecutar primero `condor
   contexto` y `condor planear`).
2. Si `plan.Status == Limited` o no hay tareas derivables: devolver `BuildResult`
   con `Status = Limited` y motivo; no se inventan acciones.
3. Por cada `PlanTask` (en orden ordinal), derivar acciones de archivo mediante
   heuristica textual determinista sobre `Title` y `Detail`:
   - si la tarea declara una ruta relativa reconocible (patron `archivo` o
     `ruta/archivo` en el detalle), se genera una accion `Actualizar` si la ruta
     existe o `Crear` si es nueva;
   - si la tarea expresa creacion de un recurso nuevo (modelo, contrato,
     componente, clase, archivo, carpeta), se genera una accion `Crear` con un
     nombre derivado acotado;
   - si la tarea expresa modificar, corregir, mejorar o actualizar un recurso
     existente, se genera una accion `Actualizar`;
   - el contenido se construye a partir del titulo y detalle de la tarea,
     normalizado y acotado a `MaxContentLength`;
   - las rutas se normalizan y validan contra `WorkingDirectory` (sin `..`, sin
     rutas absolutas); si una ruta queda fuera, la accion se omite con motivo.
4. Se truncan las acciones a `MaxActions` conservando el orden ordinal.
5. Se calculan los contadores `Applied`, `Omitted` y `Failed`.

Determinismo (patron D-E7): todas las colecciones se ordenan ordinalmente; la
unica excepcion es `GeneratedAtUtc`.

Nota: en esta version inicial la derivacion es conservadora. Una tarea se
convierte en accion solo cuando existe evidencia textual suficiente; en caso
contrario se registra la omision con motivo, sin inventar rutas ni contenidos.

### Aplicacion sobre el objetivo (Infrastructure)

`ProjectFileWriter.Apply(List<BuildAction> actions, string workingDirectory)`:
- normaliza y valida cada `RelativePath` respecto de `WorkingDirectory`;
- para `Crear`: crea directorios intermedios y el archivo si no existe; si ya
  existe, la accion se omite con motivo; si la escritura falla, la accion queda
  como fallida con motivo (sin excepcion propagada).
- para `Actualizar`: si el archivo existe, lo sobrescribe; si no existe, la
  accion se omite con motivo; si la escritura falla, queda como fallida.
- es el unico componente con IO de archivos sobre el objetivo; `BuildDeriver` es
  puro.

### Responsabilidades de capa

- Core: `BuildDeriver`, modelos y `BuildJson` (sin IO). El derivador recibe el
  plan ya cargado; no abre archivos.
- Infrastructure: `BuildService` carga el plan, delega derivacion y aplica con
  `ProjectFileWriter`; `LocalStateStore` persiste `build.json` con UTF-8 sin BOM
  (patron D-D4).
- Cli: `BuildCommand` orquesta servicio + persistencia + salida; `BuildRenderer`
  muestra la seccion `BUILD`.

### Persistencia

- `build.json` en `%LOCALAPPDATA%\Condor\state\`; artefacto derivado y
  transitorio (patron D-D9).
- Serializacion UTF-8 sin BOM (patron D-D4).
- No modifica `assessment.json`, `context.json` ni `plan.json`; no escribe en el
  repositorio del proyecto objetivo.

## Degradaciones

| Situacion | Comportamiento |
|---|---|
| Sin `WorkPlan` persistido | `NotDetected` con motivo instructivo (ejecutar `condor contexto` y `condor planear`); exit code 1 |
| Plan en `NotDetected` | `NotDetected` con motivo instructivo; exit code 1 |
| Plan en `Limited` o sin tareas derivables | `Limited` con motivo; sin inventar acciones |
| Accion con ruta fuera del objetivo | Accion omitida con motivo; el resto continua |
| Accion no aplicable (crear sobre existente, actualizar sobre inexistente) | Accion omitida con motivo; el resto continua |
| La falla de una parte | Nunca destruye el resultado completo |
