# T-016 - Experiencia de agente de ingenieria: intencion libre, preparacion automatica, control por slash y hardcodeo del motor agente

Version: 1.0.0
Estado: Completada y cerrada
Prioridad: Alta

## Objetivo

Corregir la desviacion arquitectonica detectada en la prueba manual: la CLI
convirtio las capacidades de Condor en una lista rigida de comandos. Condor debe
comportarse como un agente de ingenieria, no como un interprete de comandos, y ser
una herramienta de ingenieria realmente utilizable (no solo un router funcional).

Esta tarea abarca dos etapas:

1. **Correccion arquitectonica** (separacion de tres conceptos): preparacion
   automatica al iniciar, slash commands de control, e intencion libre como via
   de primera clase al motor agente.
2. **Hardcodeo funcional del motor agente** (brechas de utilidad real): resolucion
   fiable de rutas, edicion completa y precisa, recuperacion ante errores,
   restauracion bajo demanda, continuacion del ciclo con errores reales, y
   proteccion contra falsos positivos.

## Principio rector

No se optimiza para que las pruebas pasen; se optimiza para que Condor funcione.
El harness externo (build/test/restore reales) es la unica autoridad del resultado;
el exito jamas proviene de la declaracion del modelo. Si algo no funciona de forma
fiable, queda registrado como limitacion explicita; no se maquilla para cerrar.

## Flujo implementado

```
condor (sin argumentos)
  -> preparacion automatica (hardware, RAM, almacenamiento, GPU, Ollama, modelos,
     presupuesto seguro, seleccion/reutilizacion/instalacion)
  -> sesion interactiva (> )
     - "/xxx" -> comando de control (slash)
     - otra cosa -> intencion libre al motor agente
condor "<intencion>"  -> one-shot al motor agente

Motor agente (RunAsync):
  -> snapshot inicial de fuentes (RepoSnapshot)
  -> list_dir/read_file (rutas reales relativas, sugerencia de candidatos)
  -> patch/edit_file/create_file (edicion quirurgica con conservacion del resto)
  -> build/test/restore (harness externo real)
  -> evidencia real devuelta al modelo para decidir el siguiente paso
  -> undo_file (recuperacion ante ediciones que rompen el build)
  -> exito SOLO si: harness Done (build+test reales) Y no se modificaron pruebas
     (guarda anti-falsos-positivos)
```

## Separacion de los tres conceptos

### 1. Preparacion automatica

Al iniciar condor, Condor evalua automaticamente hardware, RAM disponible,
almacenamiento, GPU, Ollama, modelos instalados, presupuesto seguro y capacidad de
ingenieria; selecciona el modelo mas adecuado para la tarea/equipo, lo reutiliza o
lo instala si es viable, y deja el entorno preparado. Es silenciosa salvo
informacion relevante, errores o decisiones de intervencion. El usuario NO ejecuta
comandos para preparar el modelo (componente `StartupPreparer` que usa
AssessmentService + ModelAutoSetupService internamente).

### 2. Slash commands

Las capacidades explicitas de control usan `/`: `/analizar`, `/contexto`,
`/planear`, `/construir`, `/verificar`, `/avanzar`, `/examinar`, `/recomendar`,
`/consultar`, `/verificar-semantico`, `/preparar`, `/ayuda`, `/salir`. Son
herramientas de control/diagnostico y NO representan la totalidad de capacidades
ni son un requisito para desarrollar.

`/analizar` significa analisis del proyecto/directorio: estructura, contenido,
senales, estado e intencion probable. El analisis de hardware/modelos NO pertenece
a `/analizar` (forma parte de la preparacion automatica).

### 3. Intencion libre

Cualquier entrada que no comienza con "/" es una intencion natural y pasa al motor
agente. Nunca se responde "comando desconocido". No se convierten las intenciones
en aliases de `/hacer`; la entrada natural es una primera clase del sistema.

## Hallazgos importantes corregidos (evidencia)

### A. Bug critico de edicion: `patch` truncaba archivos

`AgentToolset.Patch` usaba `string.Remove(índice)` (un solo argumento), que borra
de ese indice hasta el FINAL del string. En E2E real corrompio el archivo: tras
reemplazar `a - b` por `a + b`, desaparecio el resto (metodo `Multiply` y las
llaves) y el build fallo con CS1513. Corregido a `Remove(índice, longitud)` con
`FindSnippet` (índice, longitud). Ahora `patch` es un reemplazo quirurgico real y
conserva el resto intacto, con normalizacion de CRLF.

### B. El harness "test" no ejecutaba pruebas reales

`ProcessRunner` mapeaba el verbo del agente comparandolo con la constante interna
`SemanticCheck.KindTest="probar"`. Como el agente envia `"test"` (o `"restore"`),
ambos se traducian a `dotnet build`. Es decir, el paso "test" del ciclo volvia a
compilar, NO ejecutaba las pruebas. Corregido con `NormalizeVerb(kind)`
(test/build/restore). Ahora el harness ejecuta `dotnet test` real (evidencia:
`Correctas! 1/1`) y `dotnet restore` real.

### C. Auto-restore bajo demanda (AgentHarness)

Proyectos sin restaurar fallaban el build con `NETSDK1004` (no
`project.assets.json`) y el agente no podia continuar. `AgentHarness` detecta el
fallo de restauracion y ejecuta `dotnet restore`, luego reintenta build/test.
Verificado en proyecto fresco: build(FAIL NETSDK1004) -> restore -> build -> test
= `Correctas! 1/1`.

### D. Resolucion fiable de rutas

`list_dir` devuelve rutas relativas limpias con marcadores `[d]`/`[f]` y una nota
de uso; `read_file` devuelve el contenido exacto con marcadores CONTENIDO/FIN; si
una ruta no existe se ofrecen candidatos coincidentes (p. ej. `Calculator.cs`
inexistente sugiere `App/Core/Calculator.cs`). El modelo recibe la estructura real
al iniciar y se le instruye a no inventar rutas.

### E. Continuidad del loop con evidencia real

Tras cada modificacion, el harness se ejecuta y la evidencia real (salida de
build/test) se entrega al modelo para que decida el siguiente paso (leer el
archivo señalado, `patch`, `undo_file`, `build`/`test` de nuevo). No se adivina ni
simula exito.

### F. Recuperacion (undo_file)

Nueva accion `undo_file` con pila por ruta: revierte la ultima edicion/patch/create
sobre un archivo. Verificado en E2E: tras un patch que rompio el build en un caso
ambiguo, el agente revirtio con `undo_file` y el archivo quedo integro (sin
corrupcion), para reintentar.

### G. Guarda anti-falsos-positivos (RepoSnapshot)

En un E2E real el modelo intento "resolver" la tarea modificando el archivo de
prueba (esperaba `-1` en vez de `7`) para que el test "pasara", dejando el defecto
en produccion. Para evitarlo, `AgentService` toma una instantanea de los fuentes al
iniciar (`RepoSnapshot`) y, antes de confirmar exito, verifica que NO se hayan
modificado archivos de prueba. Si se modificaron, Condor NO confirma exito y falla
honestamente indicando que debe revertir las pruebas y corregir el codigo de
produccion.

## Verificacion de que el harness es la autoridad

Las unicas sentencias que pueden devolver `Success = true` en el motor agente
estan precedidas de:
- `AgentHarness.VerifyAsync` devolvio `Done = true` (build real exit 0 Y test real
  exit 0, con auto-restore si es necesario), y
- `VerifyTestIntegrity` no detecto archivos de prueba modificados.

No existe ningun camino de exito que no pase por el harness externo + la guarda de
integridad. La declaracion del modelo nunca es autoridad.

## Limites de T-016

- **L-008**: La validacion E2E de T-016 corresponde a **proyectos .NET**. El soporte
  especializado para otros ecosistemas (TypeScript/Node, Python, Java, Go, Rust,
  etc.) queda para una evolucion posterior. NO se considera un defecto de esta tarea
  ni una promesa implicita de soporte: es un limite declarado del alcance.
- El exito del agente sobre una tarea concreta no es una garantia de resolucion
  universal: es una demostracion de capacidad sobre un caso (build/test reales como
  autoridad). En casos ambiguos o de edicion degenerada, Condor falla honestamente al
  limite de iteraciones y se recupera con `undo_file`.
- El modelo usado es el de maxima capacidad de ingenieria dentro del presupuesto
  seguro disponible; si resulta insuficiente, Condor falla honestamente sin forzar
  PASS ni seleccionar un modelo inviable.
- La sesion interactiva (`condor` sin argumentos) en terminal real no se automatizo
  en E2E (requiere stdin no redirigido); el bucle quedo cubierto por
  `InterpreterTests` y el arranque/auto-prepare por E2E no interactivo.

## Observaciones

- La seleccion del modelo es dinamica segun la RAM libre real: en este equipo, con
  mas RAM libre disponible, el modelo agente elegido fue `qwen2.5-coder:7b` (en
  T-015, con menos RAM libre, fue `qwen2.5-coder:3b`). Ambas son correctas dentro
  del presupuesto seguro: seleccion por capacidad de ingenieria conforme a la RAM
  libre real, no un modelo fijo.
