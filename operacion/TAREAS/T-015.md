# T-015 - Automatizacion de puesta en marcha y modelo LLM local

Version: 2.1.0
Estado: Completada y cerrada
Prioridad: Alta

## Objetivo

Permitir que Condor (dentro de v1.x) seleccione y asegure de forma automatica el
modelo LLM local mas adecuado para la tarea dentro de un presupuesto seguro de
recursos, alineado con la experiencia esperada de Condor: seleccionar el mejor
modelo viable, obtenerlo cuando corresponda y reutilizarlo si ya existe.

## Flujo implementado

```
Assessment
  -> evaluar hardware real (RAM total/libre, disco, GPU, Ollama)
  -> presupuesto seguro de recursos (RAM libre - margen operativo; disco libre - reserva)
  -> descartar preventivamente modelos inviables (pico > presupuesto)
  -> seleccionar por maxima capacidad de ingenieria dentro del presupuesto
     (MultiFile -> Coding -> StructuredOutput -> menor peso como desempate)
  -> comprobar inventario Ollama
  -> si el deseado ya existe: reutilizar (NO descargar nuevamente)
  -> si el deseado no existe y una alternativa instalada es tan capaz: reutilizar
  -> si no existe y cabe: obtener mediante Ollama (timeout, reintentos, verificacion)
  -> actualizar Assessment/estado
  -> continuar el flujo
```

La seleccion NO se basa en "el modelo mas pequeno que cabe" ni en "el mas potente
disponible", sino en la mejor capacidad de ingenieria que puede ejecutarse de
forma estable dentro del presupuesto seguro de RAM y disco. Si ninguna alternativa
es viable, Condor degrada de forma explicita sin fuerza/unir el resultado.

## Presupuesto seguro (ModelMemoryBudget)

- `SafeBudgetGb = max(0, ramFreeGb - margenOperativo)`. NUNCA usa un porcentaje
  de RAM total cuando la RAM libre real es menor; nunca supera la RAM libre.
- `margenOperativo = min(3.0, max(1.5, ramTotalGb * 0.08))` cubre SO, servidor
  Ollama, runtime de Condor y un colchon anti-swapping para build/test.
- Viabilidad del modelo: `pico = pesoGb * 1.2 + KVCacheContexto`, y se exige
  `pico <= SafeBudgetGb`.
- Disco: `peso + reserva_trabajo + margen_seguridad <= libreDisco`.
- Consecuencia arquitectonica: un 7B/8B no es elegible si su pico excede el
  presupuesto, aun cuando el modelo ya este instalado (no se fuerza usarlo por
  no tener que descargarlo).

## Seleccion por capacidad (ModelSelector / ModelCatalog)

- El catalogo modela variantes con parametros, cuantizacion, peso, contexto y
  perfil de capacidad de ingenieria (CodingLevel, MultiFileLevel,
  StructuredOutput, ToolUse, Stability, Purpose) por dominio (consulta/coding/
  agente/vision).
- Las variantes se verificaron contra el registro de Ollama (pesos reales).
  `qwen2.5-coder:3b` es una variante agente viable para presupuestos pequenos.
- La alternativa instalada solo se reutiliza si tiene capacidad equivalente o
  mayor que el deseado; una alternativa instalada menos capaz NO impide obtener
  el deseado mas capaz que cabe en el presupuesto.

## Evidencia

- Build Release: 0 errores, 0 advertencias.
- Pruebas unitarias (Core): 197/197 (incluye ModelMemoryBudget corregido,
  ModelSelector por capacidad y catastro de variantes).
- Pruebas de arquitectura: 22/22 (incluye ModelInterior y agente puro).
- Pruebas de integracion (Infra): 177/177 (incluye ModelAutoSetup, RetryPolicy y
  agente).
- Presupuesto corregido demostrado: con RAM libre ~4.9 GB, un 7B (pico ~5.2) NO
  es elegible pese a estar instalado; `qwen2.5-coder:3b` si lo es.
- Descarte preventivo: la seleccion automatica NO elige/descarga un modelo cuyo
  pico excede el presupuesto seguro (no se fuerza usar 7B para intentar un PASS).
- E2E REAL (proyecto temporal con defecto real, sin `--modelo`):
  - `condor analizar` fija el proyecto y RAM libre.
  - `condor hacer "corrige el error en Calculator.Sum..."` selecciono
    `qwen2.5-coder:3b` (descartando el 7B por presupuesto), lo obtuvo, y el
    agente hizo read_file -> edit_file -> build (OK) -> test (OK).
  - El harness externo confirmo build y pruebas; verficacion externa aislada:
    `dotnet test` 2/2 superadas tras la correccion. El exito NO proviene de
    declaracion del modelo, sino del build/test del harness.
- Reutilizacion: si el modelo deseado esta instalado, `condor preparar`/agente no
  vuelve a descargar (verificado por pruebas y flujo).

## Modelo seleccionado (no fijo)

- En este equipo, con RAM libre real ~4.9 GB, el modelo agente elegido es
  `qwen2.5-coder:3b` (capacidad de ingenieria viable dentro del presupuesto),
  descartando `qwen2.5-coder:7b` (pico > presupuesto) aunque este instalado.
- La eleccion no es un modelo fijo: depende del Assessment real (presupuesto) y
  de la capacidad de ingenieria para el dominio de la tarea.

## Registro de cierre

Se cierra T-015 sobre la base de evidencia funcional, no de checklist. La
capacidad queda demostrada en un ciclo agente real (E2E) y en las suites de
validacion. Quedan registrados explicitamente:

- La E2E demuestra un ciclo agente real sobre un defecto puntual
  (`Calculator.Sum`): seleccion automatica -> obtencion -> inspeccion -> edicion
  -> build/test -> verificacion externa. NO constituye una garantia de
  resolucion universal de cualquier proyecto o tarea: es una demostracion de la
  capacidad sobre un caso concreto, no una promesa de completitud arbitraria.
- El modelo `qwen2.5-coder:7b` (instalado en el equipo) fue descartado
  correctamente por presupuesto de memoria: su pico (~5.2 GB) supera el
  presupuesto seguro calculado sobre la RAM libre real (~4.9 GB) con margen
  operativo. No se fuerzo su uso por estar instalado.
- `qwen2.5-coder:3b` fue seleccionado por capacidad de ingenieria dentro del
  presupuesto seguro: es la variante de mayor capacidad (coder) que cabe de
  forma estable, frente a la alternativa general instalada menos capaz.
- Capacidades que exceden el alcance de T-015 (p. ej. resolucion automatica de
  tareas arbitrarias o multi-archivo extenso general) quedan como pendientes de
  evolucion continua; no se implementaron durante el cierre.
