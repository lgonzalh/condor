# T-011 - Vision local

Version: 1.0.0
Estado: Formalizada (contrato aprobado; pendiente de diseno e implementacion)
Prioridad: Media

## Objetivo

Implementar una capacidad local y acotada para analizar una imagen mediante un
modelo de vision local disponible, condicionada por las capacidades detectadas
por Assessment (`VisionCapable`) y por la disponibilidad real del modelo de
vision. Se materializa en el comando `condor examinar`.

Esta capacidad es de entrada multimodal del agente (analisis de una imagen a
peticion), NO se integra en Planner, Builder, Verifier ni Documenter, y NO se
ejecuta automaticamente durante el flujo completo.

## Alcance

T-011 debe:

- Implementar `condor examinar "<ruta_imagen>"` y `condor examinar "<ruta_imagen>" --json`.
- Recibir una ruta de imagen local y validar que existe y puede leerse.
- Consultar las capacidades de vision detectadas por Assessment (`VisionCapable`).
- Verificar disponibilidad de un modelo local con capacidad `vision`
  (reutilizando `ModelRoleClassifier.HasVision` y `condor recomendar --proposito vision`).
- Utilizar el modelo de vision local disponible via Ollama (extension aditiva
  multimodal).
- Devolver el resultado al usuario (texto y `--json`).
- Degradar de forma controlada cuando la capacidad no este disponible.
- No descargar modelos, no usar Internet, no usar Cloud, no integrar APIs externas.

## Extension aditiva de T-002

Se autoriza una extension ADITIVA de `ILlmClient`, `LlmRequest` y `OllamaClient`
exclusivamente para soportar entrada multimodal (imagenes):

- se anade una propiedad opcional de imagenes (base64) a `LlmRequest`, vacia por
  defecto;
- el contrato textual existente (`Prompt`, `Model`, `condor consultar`) permanece
  compatible e inalterado;
- cuando no hay imagenes, `OllamaClient` construye el mismo payload textual de
  siempre (compatibilidad verificada por prueba);
- cuando hay imagenes, se construye un `content` multimodal con texto + imagenes.

La aprobacion NO reabre T-002 ni modifica su historia congelada. La extension
debe quedar documentada y con pruebas de compatibilidad.

## Seleccion del modelo

T-011 reutiliza las capacidades existentes:

- `CapabilitiesSummary.VisionCapable` (Assessment).
- `ModelRoleClassifier.HasVision(ModelInfo)`.
- `condor recomendar --proposito vision` (seleccion/degradacion de modelo de
  vision).

No crea un sistema de recomendacion nuevo, no selecciona arbitrariamente y no
descarga modelos.

## Hardware y degradacion

La disponibilidad de vision respeta las senales de Assessment. Si no existe
capacidad de vision, modelo compatible, imagen valida o comunicacion local:

- no lanza excepcion no controlada;
- produce degradacion estructurada;
- informa el motivo;
- usa exit code no-cero cuando corresponda;
- permite salida `--json` equivalente.

No se inventan capacidades alternativas fuera de Assessment.

## Entradas

- Ruta de imagen local (`string`).
- Assessment persistido (`CapabilitiesSummary.VisionCapable`).
- Modelo de vision disponible (via Recomendador / `ModelRoleClassifier.HasVision`).

## Salidas

- `VisionResult` con: estado (`DetectionStatus`), motivo, imagen procesada (ruta
  y tamano), modelo usado, resumen del modelo (contenido) y metadata.
- Seccion `EXAMINAR` en texto y campo `vision` en `condor examinar --json`.

## Responsabilidades

| Capa | Responsabilidad |
|---|---|
| Condor.Core | Modelos de vision (`VisionResult`, `VisionLimits`), logica pura de disponibilidad (`VisionGate`): sin IO, determinista. |
| Condor.Infrastructure | `VisionService` (orquestacion: lee imagen, verifica gate, llama a Ollama multimodal) y `ImageFileReader` (IO de lectura de la imagen); extension aditiva de `OllamaClient`. |
| Condor.Cli | `ExamineCommand`, `ExamineRenderer`; comando `condor examinar`. |

## Modelo de datos multimodal (extension aditiva)

```
LlmRequest (existente)
  Model, Prompt, Temperature, MaxTokens   // inalterados
  Images: List<string>?   // NUEVO, base64, vacio por defecto

LlmResponse (existente, inalterado)
  Success, Content, Model, Error
```

## Degradaciones

| Situacion | Comportamiento |
|---|---|
| Imagen inexistente o ilegible | `Limited`/`Error` con motivo; exit code no-cero; `--json` equivalente |
| `VisionCapable == false` (Assessment) | Degradado con motivo (GPU/capacidad no detectada); sin excepcion |
| Sin modelo local con capacidad vision | Degradado con motivo (usar `condor recomendar --proposito vision`); exit no-cero |
| Ollama no disponible | Degradado con motivo de comunicacion |
| VLM no devuelve contenido | Degradado con motivo |
| Exito | `Detected` con el contenido del modelo |

## Determinismo

- Disponibilidad, validacion de entrada, seleccion y degradaciones: DETERMINISTAS.
- Contenido generado por el VLM: NO determinista (se documenta expresamente).

## Criterios de aceptacion

- `condor examinar` (texto y `--json`) en espanol sin tildes.
- Validacion de imagen, gate de vision y degradaciones correctas sin excepciones.
- Extension aditiva de T-002 sin romper `condor consultar` (texto) ni T-002
  congelada (prueba de compatibilidad).
- Determinismo en la parte no-LLM; diferencia LLM documentada.
- Sin descarga de modelos, sin Internet, sin Cloud, sin APIs externas.
- Pruebas unitarias/integracion/arquitectura + E2E real condicionada a
  hardware/modelo (o degradacion correcta documentada).
- `1 archivo = 1 commit`, publicado, HEAD == origin/main, working tree limpio.
- No modificar T-001 a T-010 fuera de la extension aditiva estrictamente
  necesaria.
