# T-004 - Descubrimiento de proyecto

Version: 1.1.0
Estado: Especificada (diseno aprobado, preparada para implementacion)
Prioridad: Alta

## Objetivo

Descubrir objetivamente el proyecto local a partir del directorio de trabajo y producir un perfil de proyecto (ProjectProfile) aditivo al Assessment, dentro de los limites aprobados, sin interpretar ni modificar el proyecto.

## Alcance

T-004 debe descubrir objetivamente un proyecto local a partir del directorio de trabajo.

Debe identificar, dentro de los limites aprobados:

- identidad y raiz del proyecto;
- si existe repositorio Git;
- rama actual;
- estado limpio o sucio;
- ultimos 5 cambios de Git (hash corto y asunto);
- lenguajes mediante senales objetivas;
- frameworks mediante senales objetivas;
- manifiestos soportados;
- dependencias de primer nivel cuando el contrato del manifiesto lo permita;
- documentacion por presencia (sin leer contenido);
- estructura de nivel superior;
- volumen observado (archivos, directorios, tamano total);
- limites aplicados;
- degradaciones.

## No alcance

T-004 NO debe:

- interpretar la intencion del usuario;
- determinar el punto de continuacion;
- resumir semanticamente el proyecto;
- localizar artefactos para continuar;
- analizar codigo;
- analizar dependencias transitivas;
- interpretar documentacion;
- evaluar deuda tecnica;
- determinar riesgos del proyecto;
- construir planes;
- modificar el proyecto descubierto;
- implementar capacidades de T-005 o posteriores.

## Entradas

- Directorio de trabajo (campo `WorkingDirectory` del Assessment).
- Sistema de archivos local.
- Repositorio Git cuando exista.
- Catalogo de senales (9 familias o ecosistemas) y modelo centralizado de limites.

## Salidas

- `ProjectProfile` como campo aditivo de `AssessmentResult` (persistido en `assessment.json`).
- Seccion `PROYECTO` en la salida de `condor analizar`.
- Campo `project` en la salida de `condor analizar --json`.

Los Assessments existentes sin el campo `Project` deben continuar siendo validos. No se crea un segundo archivo de estado. No se modifica `SchemaVersion` sin una razon tecnica formal.

## Contrato de manifiestos (D-4)

Cada manifiesto se lee hasta el limite de bytes por manifiesto con un parser de contrato fijo. Cualquier campo fuera del contrato se ignora. Un error de parseo registra `ParseError: true` y nunca produce una excepcion.

| Manifiesto | Formato | Campos permitidos | Prohibido |
|---|---|---|---|
| `package.json` | JSON | `name`, `version`, `type`; `dependencies` y `devDependencies` (solo nombres de claves) | `scripts`, `engines`, `config`, contenido de scripts, dependencias versionadas |
| `.tsconfig.json` | JSON | `compilerOptions.target`, `extends` | Todo lo demas |
| `*.csproj` | XML | Atributo `Sdk` del elemento raiz; `<TargetFramework>`, `<TargetFrameworks>`, `<UseWPF>`, `<UseWindowsForms>`; atributo `Include` de `PackageReference` y `ProjectReference` | Grupos de propiedades completos, contenido de grupos de elementos salvo los `Include` indicados |
| `pom.xml` | XML | `groupId`, `artifactId`, `version` del proyecto; `java.version` dentro de propiedades; `artifactId` de cada dependencia | `build`, `plugins`, `repositories`, dependencias transitivas |
| `Cargo.toml` | TOML | `package.name`, `package.version`; nombres de claves de `dependencies` | Dependencias de desarrollo, perfiles, seccion de binarios |
| `pyproject.toml` | TOML | `project.name`, `project.version`; `project.dependencies` (nombres) | Secciones de herramientas, sistema de compilacion |
| `requirements.txt` | Texto por linea | Nombres de paquete (texto antes de `==`, `>=`, `<=`, `~=`), maximo 100 lineas | Versiones, indices, comentarios |
| `go.mod` | Texto por linea | Linea `module <nombre>` | Lineas `require`, `replace`, `toolchain` |
| `Makefile`, `CMakeLists.txt`, `build.gradle`, `setup.py`, `*.sln`, `global.json`, `Directory.Build.props` | - | Solo presencia (nombre y tamano) | Cualquier lectura de contenido |

Los formatos sin parser se registran como senales de presencia del ecosistema.

## Exclusiones (D-3)

Lista oficial inicial de directorios excluidos, por nombre exacto en cualquier nivel de profundidad. Los directorios excluidos no se enumeran ni se cuentan. No se excluye codigo fuente.

| Directorio | Motivo |
|---|---|
| `.git` | Metadatos internos de Git, voluminosos, sin valor estructural; el estado de Git se consulta con operaciones de solo lectura |
| `node_modules` | Dependencias instaladas; decenas de miles de archivos; sin valor estructural |
| `bin` | Salidas de compilacion; regenerables |
| `obj` | Objetos intermedios de compilacion; regenerables |
| `dist` | Salidas de compilacion de interfaz; regenerables |
| `build` | Artefactos de compilacion en varios ecosistemas; regenerables |
| `.vs` | Configuracion local del IDE; no es fuente |

Si un proyecto usa un directorio excluido como fuente real, se documenta como limitacion aceptada.

## Limites centralizados (D-2)

El descubrimiento usa un modelo de limites centralizado con valores predeterminados: una unica definicion de limites que consume la logica del descubrimiento, de modo que un cambio de valores no exija modificar la logica de exploracion. No se introduce un sistema general de configuracion del proyecto.

Valores predeterminados aprobados:

| Limite | Valor predeterminado |
|---|---|
| Profundidad maxima | 6 niveles desde la raiz |
| Directorios maximos | 2000 |
| Archivos maximos | 10000 |
| Bytes maximos por manifiesto | 64 KB |
| Tamano total observado | 2 GB (al superar se marca `TotalSizeExceeded` y se deja de sumar) |
| Tiempo maximo del descubrimiento | 30 s |
| Tiempo maximo por operacion Git | 10 s |
| Manifiestos leidos | 50 |
| Dependencias listadas por manifiesto | 100 |
| Cambios Git | 5 |
| Asunto de cambio Git | 80 caracteres |
| Hash de cambio Git | 8 caracteres |

Razon de los valores: permiten terminar el descubrimiento de forma determinista y segura sobre proyectos reales, sin depender de conteos infinitos, y protegen el tiempo de procesamiento y la memoria.

## Modelo ProjectProfile (D-5)

Contrato tecnico del campo aditivo (los nombres forman parte del esquema tecnico del Assessment):

```
AssessmentResult
  + Project: ProjectProfile?   // null en Assessments previos; el Assessment sigue siendo valido

ProjectProfile
  Status            DetectionStatus   // Detected, NotDetected, Error o Limited
  Reason            string?           // motivo de degradacion
  RootPath          string            // ruta absoluta del directorio de trabajo
  RootName          string            // nombre de la carpeta raiz
  IsGitRepository   bool
  Git               GitProjectState?  // null si no es repositorio Git o git no esta disponible
  Languages         List<LanguageEvidence>   // ordenado por nombre
  Frameworks        List<FrameworkEvidence>  // ordenado por nombre
  Manifests         List<ManifestInfo>       // ordenado por ruta relativa
  Documentation     List<DocumentationInfo>  // ordenado por ruta relativa
  TopLevelDirectories List<string>            // nivel 1, ordenado
  TopLevelFiles     List<string>              // nivel 1, ordenado
  ExtensionCounts   List<ExtensionCount>      // agregacion ordenada
  DirectoriesCount  int
  FilesCount        int
  TotalSizeBytes    long
  TotalSizeExceeded bool
  LimitsApplied     List<string>       // limites que se activaron
  GeneratedAtUtc    DateTime           // metadata, no senal

LanguageEvidence
  Name      string             // nombre de la familia/ecosistema
  Primary   bool               // true si hay evidencia de manifiesto; false si solo extensiones
  Signals   List<EvidenceSignal>

EvidenceSignal
  Kind      EvidenceKind       // Manifest, Extension o Folder
  Value     string
  Count     int?               // para extensiones: cantidad de archivos

FrameworkEvidence
  Name      string
  Signal    string             // descripcion de la senal
  Manifest  string             // ruta relativa del manifiesto origen

ManifestInfo
  Kind        string
  Path        string           // ruta relativa
  Name        string?
  Version     string?
  Dependencies List<string>    // maximo 100
  ParseError  bool
  SizeBytes   long

DocumentationInfo
  Kind      string             // README, LICENSE, CHANGELOG o docs
  Path      string             // ruta relativa
  SizeBytes long

GitProjectState
  Branch    string?
  IsDirty   bool
  Commits   List<GitCommitSummary>  // ultimos 5
  Status    DetectionStatus

GitCommitSummary
  Hash      string             // 8 caracteres
  Subject   string             // truncado a 80 caracteres
```

Reglas de compatibilidad:

- `SchemaVersion` se conserva en `1.0.0`; el campo `Project` es aditivo.
- Un Assessment existente sin `Project` se deserializa con `Project` en null y sigue siendo valido para todos los consumidores actuales.
- El campo `project` solo se emite en JSON cuando el perfil existe.
- Se agrega una prueba que cargue un `assessment.json` previo sin `project` y verifique su validez.

## Determinismo (D-6)

Misma ruta y mismo estado del proyecto producen el mismo perfil, con la unica excepcion de `GeneratedAtUtc` (metadata).

Reglas:

- Todas las colecciones se ordenan por nombre (comparacion ordinal) antes de construir el resultado: lenguajes, frameworks, manifiestos, documentacion, conteos de extension, carpetas y archivos de nivel superior.
- Los conteos por extension se construyen como agregacion y se convierten a lista ordenada; nunca se conserva el orden del sistema de archivos.
- No se usan marcas temporales de archivos como senales.
- El parseo de manifiestos lee por nombre de propiedad; el orden de claves no altera el resultado.
- Una prueba ejecuta el descubrimiento dos veces sobre el mismo directorio y compara la serializacion (excluyendo `GeneratedAtUtc`).

## Seguridad (D-7)

Reglas formales:

- La ruta de trabajo es la frontera del descubrimiento.
- No se siguen enlaces simbolicos ni junctions (elementos con atributo de punto de reanalisis): se registran por nombre y no se desciende sobre ellos.
- No se escapa de la raiz: toda ruta se construye dentro de la raiz y se valida con ruta completa; cualquier intento de escape se registra como limitacion y se descarta.
- No se utilizan rutas `..` para recorrer el proyecto.
- No se lee el contenido de archivos sensibles (secretos o credenciales): sus nombres pueden observarse; abrir o leer su contenido esta prohibido por contrato.
- No se leen archivos binarios: se identifican por extension y solo se cuentan.
- Los archivos que no son manifiesto no se abren para analizar contenido.
- Los manifiestos solo se leen mediante contratos acotados (D-4).
- El acceso denegado degrada el descubrimiento por elemento; no lo detiene por completo.
- Los limites de volumen son obligatorios.
- Git se consulta solamente mediante operaciones de solo lectura.
- No se utiliza red, servicios cloud ni descarga de informacion.

Patrones sensibles (prohibidos de leer): `.env*`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, `secrets.*`, `credentials*`, `*.npmrc`, claves privadas (`id_rsa*`), `*.jks`.

## Degradaciones

| Situacion | Comportamiento |
|---|---|
| Ruta inexistente | Perfil con estado `NotDetected` y motivo; exit code 1; sin excepcion |
| Ruta no accesible | Estado `Error` con motivo; resto del perfil ausente |
| Directorio vacio | Perfil valido sin estructura, sin lenguaje; no es un error |
| Proyecto muy grande | Descubrimiento parcial con limites aplicados y declarados en `LimitsApplied` |
| Archivos no soportados | Se ignoran (solo conteo por extension); no bloquean |
| Sin archivos relevantes | Perfil sin senales de lenguaje, con estructura observada; no se inventan interpretaciones |
| Sin Git | Perfil sin seccion Git; sin error |
| Repositorio Git degradado | Seccion Git en `Error` con motivo; el resto del perfil se conserva |
| Manifiesto corrupto o fuera de contrato | `ParseError: true` en el manifiesto; sin excepcion |
| Acceso denegado parcial | Elemento omitido; perfil en `Limited` con motivo |
| El fallo de una parte del descubrimiento | Nunca destruye el perfil completo |

## CLI (D-8)

La capacidad se integra en `condor analizar`. No se crea un nuevo comando publico.

### `condor analizar`

Se agrega la seccion `PROYECTO` al resultado en texto, con el mismo estilo de las secciones existentes:

```
PROYECTO
  Nombre: condor
  Ruta: C:\...\condor
  Git: rama main | estado sucio | ultimos 5 cambios
  Lenguajes: C# (senal: *.csproj)
  Frameworks: ninguno identificado
  Manifiestos: 3
  Documentacion: README.md, docs/
  Estructura: Docs, Src, Tests, operacion
  Volumen: 3450 archivos / 210 directorios / 145,2 MB
  Limites aplicados: ninguno
```

Reglas del texto visible:

- Espanol latinoamericano sin tildes y sin spanglish.
- `rama`, `sucio`/`limpio`, `cambios`, `ruta`, `archivo`, `directorio`, `carpeta`, `estado`, `proyecto`.
- Si no hay Git: `Git: no es un repositorio Git.`
- Si hay degradacion: linea de estado del descubrimiento con el motivo (patron de las degradaciones existentes).
- Si no hay senales de lenguaje: `Lenguajes: no identificados (estructura desconocida o sin senales)`.
- Frameworks solo si hay senal manifiesta; si no: `Frameworks: ninguno identificado.`

### `condor analizar --json`

La salida JSON incluye el campo `project` de acuerdo con el contrato tecnico aprobado (D-5). Los nombres del JSON forman parte del esquema tecnico del Assessment y pueden permanecer en ingles.

## Frontera T-004 / T-005 (D-9)

T-004:

```
Proyecto local
→ observacion
→ senales objetivas
→ estructura
→ estado
→ ProjectProfile
```

T-005:

```
ProjectProfile
→ interpretacion
→ contexto
→ comprension
→ punto de continuacion
```

T-004 no debe anticipar ninguna capacidad propia del Context Engine. La frontera es estricta:

- T-004 entrega a T-005: identidad y raiz, estado Git basico, lenguajes y frameworks con su evidencia, manifiestos y dependencias de primer nivel, documentacion por presencia, estructura y volumenes observados, limites aplicados.
- Queda fuera de T-004: interpretar la intencion, determinar el punto de continuacion, resumir semanticamente, localizar artefactos para continuar, recuperar decisiones, diferenciar idea nueva de proyecto existente, leer documentacion para resumirla, dependencias transitivas, analisis de codigo, deuda y riesgos.

## Dependencias

- T-001: directorio de trabajo, patron de persistencia del Assessment y patron de detectores con degradacion.
- T-002: operaciones de proceso con tiempo maximo (ProcessProbe).
- T-003: patron de logica pura en Condor.Core (ningun acoplamiento funcional).

## Pruebas

- Unitarias: clasificacion de senales, prioridad de evidencia, agregacion, limites, exclusiones, contrato de manifiestos, determinismo.
- Integracion con directorios de ejemplo: C#, Node, Python, vacio, grande, con archivos sensibles, con enlace simbolico, sin Git, repositorio Git limpio y sucio, manifiesto corrupto, estructura desconocida.
- Arquitectura: la logica pura permanece en Condor.Core sin I/O; la exploracion y las lecturas permanecen en Condor.Infrastructure.
- Compatibilidad: un `assessment.json` previo sin `project` se lee y sigue siendo valido.
- E2E real: descubrimiento sobre el propio repositorio Condor y sobre un directorio sin Git.
- Determinismo: dos ejecuciones sobre el mismo directorio producen el mismo perfil (excepto `GeneratedAtUtc`).

## Criterios de aceptacion

- Perfil real y objetivo sobre un repositorio real.
- Compatible con Assessments existentes (campo aditivo).
- Determinista en el mismo estado del proyecto.
- Degradaciones correctas sin excepciones.
- Funciona sin internet.
- Limites aplicados y declarados.
- No modifica el proyecto descubierto.
- Evidencia automatizada y funcional.
- Documentacion operativa actualizada.
- Continuidad posible sin esta conversacion.

## Diseno aprobado

El diseno tecnico de T-004 fue aprobado y queda documentado en `Docs/04_Razonamiento/DECISIONES.md` (DEC-027, decisiones D-D1 a D-D7):

- D-D1: `DetectionStatus` se amplia con `Limited` al final de la enumeracion (aditivo; numeracion existente conservada).
- D-D2: `ProcessProbe.RunAsync` admite un directorio de trabajo opcional (comportamiento actual por defecto) para las operaciones Git.
- D-D3: los parsers de manifiestos residen en `Condor.Core.Project` como logica pura y reciben solo texto acotado y metadatos; `ManifestFileReader` (Infrastructure) es el unico componente autorizado a abrir archivos; los parsers no realizan IO.
- D-D4: un manifiesto mayor de 64 KB no se parsea: `ParseError: true`, `SizeBytes` real y `manifest-size` en `LimitsApplied`; sin campos nuevos.
- D-D5: HEAD detached o repositorio sin commits: `Branch` en null y `Commits` vacio, sin error.
- D-D6: el motivo de degradacion del descubrimiento se muestra en la seccion PROYECTO; no se agrega a `Capabilities.Issues`.
- D-D7: `GitRepositoryProbe` recibe el path de git desde `Tools.Git.Path` y no vuelve a buscarlo.

La tarea queda preparada para implementacion. El alcance aprobado en este documento no se modifica por el diseno.
