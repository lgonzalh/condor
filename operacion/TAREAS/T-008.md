# T-008 - Verificacion inicial

Version: 1.0.0
Estado: Cerrada y congelada (completada, verificada, integrada y publicada)
Prioridad: Alta

## Objetivo

Implementar la version inicial del Verifier (ARQ-007 / FN-008): comprobar que
los cambios declarados como aplicados por T-007 (`BuildResult`) fueron escritos
de forma correcta, completa y acotada sobre el proyecto objetivo, siguiendo el
flujo del Kernel (Planner -> Builder -> Verifier). El Verifier no define el
QUE cambia (T-006) ni el COMO se escribe (T-007): comprueba QUE lo construido
fue aplicado correctamente.

El Verifier no improvisa (ADN Condor): verifica de forma determinista y trazable
la integridad y acotacion de la escritura sobre el proyecto objetivo, sin
depender del historial de conversaciones ni del LLM.

## Alcance

T-008 debe transformar el `BuildResult` de T-007 en un resultado de verificacion
dentro de los limites aprobados:

- Consumir el `BuildResult` persistido (via `IStateStore.LoadBuildAsync`):
  `Status`, `Reason`, `WorkingDirectory`, `RootName`, `Objective`, `Actions`,
  `Applied`, `Omitted`, `Failed` y `LimitsApplied`.
- Consumir el `ProjectContext` persistido (via `IStateStore.LoadContextAsync`)
  como base de referencia (`WorkingDirectory` y `RootName`), coherente con
  T-005:185 (T-008 usa el contexto como base de verificacion).
- Verificar que los archivos declarados como **aplicados** por T-007 realmente
  existen en el `WorkingDirectory` con su contenido declarado por `BuildAction.Content`.
- Verificar que las rutas de todas las acciones permanecen dentro del
  `WorkingDirectory` (rechazo de fugas), aplicando defensa de containment aunque
  T-007 ya lo garantice por diseno.
- Registrar cada verificacion mediante un `VerificationCheck` con estado y motivo.
- Producir un resultado de verificacion (`VerificationResult`) trazable con
  contadores (pasadas / fallidas / informativas).
- Exponer la capacidad mediante un comando publico nuevo: `condor verificar`
  (texto y `--json`), en espanol sin tildes.
- Persistir `verification.json` como artefacto derivado y transitorio en el
  estado local, sin escribir conocimiento permanente en el proyecto objetivo.
- Mantener el determinismo: mismo `BuildResult` y mismo estado de archivos
  producen el mismo resultado, con la unica excepcion de `GeneratedAtUtc`.
- Aplicar `VerificationLimits` (l�mites centralizados del Verifier).

### Ambito de la verificacion

| Situacion declarada por T-007 | Verificacion |
|---|---|
| Accion `aplicada` (Crear) | El archivo existe en `WorkingDirectory\\ruta` y su contenido es igual al declarado |
| Accion `aplicada` (Actualizar) | El archivo existe y su contenido es igual al declarado |
| Accion `omitida` | Registro informativo: no debe considerarse falla; se reporta como no aplicada con su motivo |
| Accion `fallida` | Registro informativo: no debe considerarse falla; se reporta como no aplicada con su motivo |
| Ruta fuera del `WorkingDirectory` | Check de acotacion fallida (defensa de containment) |
| Archivo esperado que no existe | Check fallida |
| Contenido distinto al declarado | Check fallida |

### Flujo de datos

```
condor verificar
  -> VerifyCommand.ExecuteAsync(verificationService, stateStore, args)
  -> VerificationService.VerifyAsync()
      -> stateStore.LoadBuildAsync()              // BuildResult persistido (T-007)
      -> stateStore.LoadContextAsync()            // ProjectContext persistido (T-005)
      -> si no hay build: VerificationResult NotDetected (motivo instructivo)
      -> ProjectFileProbe.Read(actions, workingDirectory)   // IO de lectura acotada
      -> Verifier.Verify(result, probed, limits)            // logica pura
      -> VerificationResult
  -> stateStore.SaveVerificationAsync(result)     // persiste verification.json (derivado)
  -> texto: VerifyRenderer.RenderVerification(result)
    json: Console.WriteLine(VerificationJson.Serialize(result))
  -> exit code: 1 si Status == NotDetected, si no 0
```

### Logica de verificacion (pura)

`Verifier.Verify(BuildResult? build, ProjectContext? context, IReadOnlyDictionary<string, ProbedFile> probed, VerificationLimits limits)` (Core, sin IO):

1. Si `build` es null o `build.Status == NotDetected`: devolver `VerificationResult`
   con `Status = NotDetected` y motivo instructivo (ejecutar `condor construir`).
2. Si `build.Status == Limited` o `build` no tiene acciones: devolver
   `VerificationResult` con `Status = Limited` con motivo; no se inventan checks.
3. Determinar `WorkingDirectory` con prioridad: `build.WorkingDirectory`; si esta
   vacia, usar `context.WorkingDirectory`. Si ambas vacias, degradar a `Limited`
   (sin base de verificacion).
4. Por cada `BuildAction` (en orden ordinal, hasta `MaxChecks`):
   - validar acotacion de la ruta (sin `..`, sin absoluta, sin `:`): si falla,
     check `fallida` con motivo de containment;
   - si `action.Status == "aplicada"`:
     - leer el archivo real en la ruta y comparar su contenido con `action.Content`
       (hasta `MaxContentLength`): si existe y coincide, check `pasada`; si no
       existe o no coincide, check `fallida`;
   - si `action.Status` es `omitida` o `fallida`: check `informativa` con el
     motivo del estado; no es una falla del Verifier;
   - si la ruta esta dentro del objetivo pero el archivo no existe cuando se
     esperaba existir, se registra como `fallida` de integridad.
5. Se calculan los contadores `Passed`, `Failed` y `Informative`.
6. `Checks` se truncan a `MaxChecks` con orden ordinal y ruta estable.

Determinismo (patron D-E7): todas las colecciones se ordenan ordinalmente
(rutas por orden ordinal de aparicion); la unica excepcion es `GeneratedAtUtc`.

### Lectura real (Infrastructure)

`ProjectFileProbe.Read(actions, workingDirectory)` es el unico componente con IO
de lectura sobre el objetivo. Retorna para cada accion la informacion del archivo
existente (ruta normalizada y contenido hasta `MaxContentLength`). No escribe
nada.

### Responsabilidades de capa

- Core: `Verifier`, modelos y `VerificationJson` (sin IO). El Verifier recibe la
  informacion ya leida del objetivo; no abre archivos.
- Infrastructure: `VerificationService` carga `BuildResult`/`Context`, delega
  lectura en `ProjectFileProbe` y comparacion en `Verifier`; `LocalStateStore`
  persiste `verification.json` con UTF-8 sin BOM (patron D-D4).
- Cli: `VerifyCommand` orquesta servicio + persistencia + salida; `VerifyRenderer`
  muestra la seccion `VERIFICACION`.

### Persistencia

- `verification.json` en `%LOCALAPPDATA%\Condor\state\`; artefacto derivado y
  transitorio (patron D-D9).
- Serializacion UTF-8 sin BOM (patron D-D4).
- No modifica `assessment.json`, `context.json`, `plan.json` ni `build.json`; no
  escribe en el repositorio del proyecto objetivo.

## Degradaciones

| Situacion | Comportamiento |
|---|---|
| Sin `BuildResult` persistido | `NotDetected` con motivo instructivo (ejecutar `condor contexto`, `condor planear` y `condor construir`); exit code 1 |
| Build en `NotDetected` | `NotDetected` con motivo instructivo; exit code 1 |
| Build en `Limited` o sin acciones | `Limited` con motivo; sin inventar checks |
| Sin `WorkingDirectory` (build ni contexto) | `Limited` con motivo (sin base de verificacion) |
| Ruta fuera del objetivo | Check `fallida` con motivo de containment |
| Archivo esperado inexistente | Check `fallida` de integridad |
| Contenido distinto al declarado | Check `fallida` |
| Accion omitida/fallida declarada | Check `informativa`; no es falla |
| Error de lectura puntual | Check `fallida` con motivo; el resto continua |
